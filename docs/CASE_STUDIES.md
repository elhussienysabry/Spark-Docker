# Business Case Studies

> **Status**: four runnable, end-to-end case studies built on the same Docker lab.
> **Data**: deterministic synthetic datasets generated by `data/generate_case_studies.py`.
> **Notebooks**: `notebooks/14_business_case_studies/`.
> **Last local execution**: 2026-11-11, Spark 4.2.1, `local[2]`, zero cell errors.

These case studies are the bridge between individual Spark topics and the messy shape of
real work: ambiguous metrics, missing timestamps, delayed labels, skewed keys, and
stakeholders who need a decision rather than a DataFrame.

They are **teaching cases**, not production systems. The companies, carriers, cells, and
merchants are hypothetical. Every number printed by a notebook comes from the
deterministic lab data; any cost, saving, or revenue range quoted in the narrative is
labelled as an illustration.

## 2. Running the case studies

### Option A: JupyterLab

1. Start the stack with `docker compose up -d`.
2. Open <http://localhost:8888/?token=spark>.
3. Navigate to `notebooks/14_business_case_studies/`.
4. Open a notebook and run all cells.

The notebooks read `SPARK_MASTER` from the environment and default to
`spark://spark-master:7077`. On the four-core lab, one case study at a time is enough.

### Option B: command line, cluster mode

```bash
docker exec -w /home/jovyan/work/14_business_case_studies spark-jupyter \
  jupyter nbconvert --to notebook --execute 01_ecommerce_analytics.ipynb \
  --output /tmp/01_ecommerce_analytics.ipynb \
  --ExecutePreprocessor.timeout=900
```

### Option C: command line, local fallback

Use this when the standalone cluster has no free cores or when you want a quick
correctness check without waiting for executor allocation:

```bash
docker exec -e SPARK_MASTER='local[2]' \
  -w /home/jovyan/work/14_business_case_studies spark-jupyter \
  jupyter nbconvert --to notebook --execute 01_ecommerce_analytics.ipynb \
  --output /tmp/01_ecommerce_analytics.ipynb \
  --ExecutePreprocessor.timeout=900
```

`local[2]` changes only where the work runs. The code, schemas, metrics, and outputs are
the same. Do not present local-mode timings as cluster benchmarks.

### Regenerating the data and notebooks

```bash
python3 data/generate_case_studies.py     # deterministic CSV inputs
python3 scripts/generate_case_studies.py  # rebuild the four notebooks
```

The data generator is seeded. Re-running it should produce identical row counts and
metric values; if it does not, treat that as a reproducibility bug.

## 3. Case study 1: E-commerce revenue, retention, and order outcomes

**Notebook**: [`01_ecommerce_analytics.ipynb`](../notebooks/14_business_case_studies/01_ecommerce_analytics.ipynb)  
**Inputs**: `/opt/spark-data/retail/{orders,customers,products}.csv`  
**Output**: `/opt/spark-data/case_studies/curated/ecommerce_sales/`

### Business context

A retailer has twelve months of order lines, a customer dimension, and a product catalog.
Finance, merchandising, and marketing each report a different revenue number. The case
asks for one order-grain fact with explicit definitions, then four marts: monthly revenue
and growth, category/product performance, cohort retention, and RFM segments.

### Data model

| Table | Rows | Key | Important fields |
|---|---:|---|---|
| `orders` | 60,000 | `order_id` | customer, product, timestamp, quantity, unit price, discount, status, channel |
| `customers` | 8,000 | `customer_id` | country, region, segment, loyalty tier, signup date |
| `products` | 300 | `product_id` | name, category, list price, cost, launch date, active |

Metric definitions are part of the contract:

- **Net revenue** = `quantity * unit_price * (1 - discount)`.
- **Margin** = net revenue minus `quantity * product.cost`.
- **Completed order** = `status = 'Completed'`.
- **AOV** = net revenue / distinct completed orders.
- **Guest order** = missing `customer_id`; included in revenue, excluded from
  customer-level analysis.

### Pipeline

```text
orders.csv ──┐
customers.csv ├─ explicit schemas ─ quality gate ─ broadcast joins ─ enriched sales
products.csv ─┘                                              │
                                                             ├─ monthly revenue + MoM
                                                             ├─ category/product ranking
                                                             ├─ cohort retention
                                                             ├─ RFM segments
                                                             └─ order outcomes
                                                             │
                                                             v
                                              partitioned Parquet mart
```

The small dimensions are broadcast. The enriched fact is cached only because five
analyses reuse it. Grouping and window operations still shuffle; eight shuffle partitions
are a lab setting, not a production recommendation.

### Expected results from the lab run

| Metric | Result | Interpretation |
|---|---:|---|
| Order rows | 60,000 | One row per order line |
| Months | 12 (2025-01 to 2025-12) | Full-year synthetic history |
| Completed orders | 50,930 | 84.9% of all orders |
| Net revenue, completed orders | 144,496,453.43 | Sum of discounted line revenue |
| Guest orders | 655 | About 1.1%; excluded from customer analysis |
| Gross margin | about 34.5% | Varies slightly by month and category |
| Electronics share of revenue | about 80% | Product 1 is intentionally skewed |
| Cancelled / returned | 4,237 / 3,017 | About 7.1% / 5.0% of all orders |
| RFM segments | 5 | Champions, Loyal, New/promising, Needs attention, At risk |
| Curated mart rows | 60,000 | Read back from Parquet |

The notebook also prints a physical plan showing broadcast joins and a Parquet write with
`order_month` partitions.

### Production notes

- Publish one metric dictionary; revenue disputes usually start with definitions, not code.
- Deduplicate by `order_id` with a deterministic tie-breaker before aggregating.
- Define a restatement window for late orders and backfills.
- Treat product category as an as-of-order attribute if the catalog changes.
- Compact small output files; a monthly partition should not become thousands of tiny
  files.
- Reconcile the mart total to the source total before declaring success.

### Caveats

Product 1 is deliberately hot, so product rankings are not representative. The data is
synthetic and small; the case teaches the shape of the pipeline, not a real merchandising
strategy.

## 4. Case study 2: Telecom network quality and capacity

**Notebook**: [`02_telecom_network_analytics.ipynb`](../notebooks/14_business_case_studies/02_telecom_network_analytics.ipynb)  
**Inputs**: `/opt/spark-data/case_studies/telecom/{towers,network_events}.csv`  
**Outputs**: `/opt/spark-data/case_studies/curated/telecom_cell_health/` and
`telecom_events/`

### Business context

NileConnect operates eight cell sites across Cairo, Alexandria, the Delta, Upper Egypt,
and the Canal region. The network operations center sees averages, not tails. Capacity
requests are argued from raw event counts. The case builds a cell health scorecard,
busy-hour ranking, region/technology comparison, and a customer-impact proxy.

### Data model

| Table | Rows | Key | Important fields |
|---|---:|---|---|
| `network_events` | 36,000 | `event_id` | timestamp, customer, tower, event type, bytes, latency, throughput, PRB utilization, dropped, plan, device |
| `towers` | 8 | `tower_id` | site, city, region, technology, capacity |

Key definitions:

- **Drop rate** = dropped events / all events. This is an availability proxy, not a
  session-level call-drop KPI.
- **p95 latency** = 95th percentile of data-event latency. Voice and SMS rows have zero
  latency and are excluded.
- **PRB utilization** = physical resource block utilization, a capacity-pressure signal.
- **Busy hour** = the hour with the most events per cell.
- **Congestion flag** = PRB >= 80% or drop rate >= 2%. This is a teaching rule.

### Pipeline

```text
network_events.csv ── explicit schema ── quality gate ── broadcast tower dimension
                                                              │
                                              cleaned event fact (cached)
                                                              │
                     ┌────────────────────┬───────────────────┼───────────────────┐
                     v                    v                   v                   v
               cell health           busy hour          region/technology    customer impact
                     │                    │                   │                   │
                     └────────────────────┴───────────────────┴───────────────────┘
                                                              │
                                                              v
                                                   curated Parquet outputs
```

`percentile_approx` computes the latency tail in one distributed pass instead of
collecting every value to the driver. The busy-hour query groups by cell and hour, then
ranks within each cell.

### Expected results from the lab run

| Metric | Result | Interpretation |
|---|---:|---|
| Event rows | 36,000 | One week of voice, SMS, and data events |
| Towers | 8 | Small broadcast dimension |
| Missing tower IDs | 155 | About 0.43%; quarantined from cell analysis |
| Dropped events | 391 | 1.09% overall |
| Average data latency | 24.1 ms | Mean is not the SLA |
| p95 data latency | 44 ms | Tail customers actually feel |
| Average throughput | 2.55 Mbps | Synthetic values |
| Average PRB utilization | 49.5% | Capacity headroom on average |
| TWR-001 drop rate | 2.55% | Highest cell; flagged for review |
| TWR-001 PRB utilization | 52.6% | Not the only congestion signal |
| 4G vs 5G p95 latency | 48 ms vs 32 ms | Synthetic technology comparison |
| 4G vs 5G drop rate | 0.58% vs 1.48% | 5G carries more data traffic in the generator |
| Curated cell rows | 8 | One row per tower |

The case is intentionally a warning against a single ranking: TWR-001 has the highest
drop rate but not the highest utilization. Capacity decisions need both.

### Production notes

- Use event time for windows and track ingestion time separately.
- Define a lateness bound and a reconciliation path; do not silently drop late events.
- Version the tower dimension so region and technology history are preserved.
- Alert on volume drops as well as quality thresholds; a silent cell can look healthy.
- Suppress percentile metrics below a minimum event count.
- At production scale, hot cells can create stragglers; salting or AQE skew handling may
  be required.

### Caveats

`dropped` is an event-level flag, not a session outcome. A real network-quality model
needs sessionization and a call-quality dataset. The generator deliberately makes TWR-001
hot, so the ranking is illustrative.

## 5. Case study 3: Financial transaction fraud patterns

**Notebook**: [`03_financial_fraud_patterns.ipynb`](../notebooks/14_business_case_studies/03_financial_fraud_patterns.ipynb)  
**Inputs**: `/opt/spark-data/case_studies/fraud/{transactions,merchants}.csv`  
**Outputs**: `/opt/spark-data/case_studies/curated/fraud_alerts/` and `fraud_scored/`

### Business context

SecurePay is a hypothetical payment processor with 30,000 card transactions over 30 days.
Exactly 600 transactions carry a synthetic fraud label and one of three pattern names:
card testing, account takeover, or unusual geography. The risk team needs a ranked review
queue, an explicit threshold trade-off, and evidence about which rules contribute.

### Data model

| Table | Rows | Key | Important fields |
|---|---:|---|---|
| `transactions` | 30,000 | `transaction_id` | card, customer, merchant, amount, channel, country, IP country, device, event time, synthetic label |
| `merchants` | 12 | `merchant_id` | name, category, risk tier, country |

Six explainable rules produce an integer score:

| Rule | Condition | Intent |
|---|---|---|
| Card testing | amount <= 5 and online | Tiny charges used to test stolen cards |
| Geo mismatch | transaction country != IP country | Account takeover or stolen card |
| High amount + foreign | amount >= 500 and country mismatch | Higher loss per event |
| High amount online | amount >= 700 and online | Large online basket |
| Odd-hour high amount | 00:00–05:59 and amount >= 300 | Unusual behavior |
| Velocity | >= 5 transactions on one card in 10 minutes | Burst abuse |

The score is a prioritization device, **not a calibrated probability of fraud**.

### Pipeline

```text
transactions.csv ──┐
                   ├─ explicit schema ─ quality gate ─ broadcast merchant dimension
merchants.csv ─────┘                                      │
                                                          v
                                              cleaned transaction fact
                                                          │
                                      event-time velocity window (10 min, by card)
                                                          │
                                              rule flags + integer score
                                                          │
                                     ┌────────────────────┴────────────────────┐
                                     v                                         v
                             threshold sweep                            alert dataset
                          (precision / recall)                        (analyst review)
```

The velocity window partitions by card and orders by event timestamp. That is a shuffle
plus a sort; a high-volume card can become a straggler. The threshold sweep is computed
from one grouped count by score, not one full scan per threshold.

### Expected results from the lab run

| Metric | Result | Interpretation |
|---|---:|---|
| Transactions | 30,000 | One authorization attempt per row |
| Synthetic frauds | 600 | 2.0% of transactions |
| Fraud patterns | 200 each | Card testing, account takeover, unusual geography |
| Geo-mismatch rows | 1,781 | Most are legitimate travel, VPN, or proxy traffic |
| Threshold 2 alerts | 430 | About 1.4% of transactions |
| True positives / false positives | 402 / 28 | Precision 0.935 |
| False negatives | 198 | Recall 0.670 |
| True negatives | 29,372 | Most transactions are cleared |
| Threshold 1 | 2,434 alerts | Precision 0.247, recall 1.000 |
| Threshold 3 | 102 alerts | Precision 1.000, recall 0.170 |
| Threshold 4 | 18 alerts | Precision 1.000, recall 0.030 |
| Pattern recall | 49% / 60% / 92% | Account takeover / card testing / unusual geography |

Rule contribution at the selected threshold:

| Rule | Flagged | True positives | Precision |
|---|---:|---:|---:|
| `rule_velocity` | 120 | 120 | 1.000 |
| `rule_high_amount_foreign` | 241 | 232 | 0.963 |
| `rule_high_amount_online` | 223 | 200 | 0.897 |
| `rule_odd_hour_high` | 188 | 115 | 0.612 |
| `rule_card_testing` | 431 | 200 | 0.464 |
| `rule_geo_mismatch` | 1,781 | 255 | 0.143 |

The last row is the important lesson: a rule can have high recall and terrible precision.
Aggregate precision also hides that account-takeover recall is only 49%.

### Production notes

- Labels arrive weeks later; join them as-of the decision time to avoid leakage.
- Store feature values with event time and ingestion time.
- Persist rule flags, score, rule version, and threshold for auditability.
- Monitor alert volume, precision proxies, drift, and missed patterns.
- Keep a human in the loop; automated blocking can cause unacceptable customer harm.
- Evaluate at a fixed analyst capacity, not at the threshold that maximizes recall.

### Caveats

The labels are synthetic and complete. Real labels are delayed, biased, and incomplete.
This notebook teaches mechanics and honest evaluation; it does **not** validate a
production fraud system.

## 6. Case study 4: Logistics on-time delivery and carrier performance

**Notebook**: [`04_logistics_delivery_analytics.ipynb`](../notebooks/14_business_case_studies/04_logistics_delivery_analytics.ipynb)  
**Inputs**: `/opt/spark-data/case_studies/logistics/{hubs,shipments}.csv`  
**Outputs**: `/opt/spark-data/case_studies/curated/logistics_carrier_scorecard/` and
`logistics_shipments/`

### Business context

TransExpress moves parcels through ten hubs in Egypt, the Gulf, and Europe. Four carriers
report on-time performance with different definitions. Operations is renegotiating
contracts and needs a carrier scorecard, lane ranking, service-level view, and late-driver
analysis built on one explicit denominator.

### Data model

| Table | Rows | Key | Important fields |
|---|---:|---|---|
| `shipments` | 20,000 | `shipment_id` | origin, destination, carrier, service, ship/promise/delivery timestamps, status, weight, cost, distance |
| `hubs` | 10 | `hub_id` | city, region, country, coordinates |

Key definitions:

- **Transit days** = delivered timestamp minus ship timestamp, in elapsed days.
- **On time** = delivered timestamp <= promised timestamp, defined only for shipments with
  `status = 'Delivered'` and a valid delivery scan.
- **On-time rate** = on-time deliveries / deliveries with a valid scan. Missing scans are
  reported separately, never counted as late.
- **Cost per kg** = total cost / total weight, excluding zero or missing weights.
- **Lane** = origin hub -> destination hub; a lane can have several service levels.

### Pipeline

```text
shipments.csv ──┐
                ├─ explicit schema ─ quality gate ─ broadcast origin/destination hubs
hubs.csv ───────┘                                         │
                                                          v
                                                cleaned shipment fact
                                                          │
                     ┌────────────────────┬───────────────┼───────────────────┐
                     v                    v               v                   v
              carrier scorecard       lane ranking   service/distance    weekly trend
                     │                    │               │                   │
                     └────────────────────┴───────────────┴───────────────────┘
                                                          │
                                                          v
                                                  curated Parquet outputs
```

### Expected results from the lab run

| Metric | Result | Interpretation |
|---|---:|---|
| Shipments | 20,000 | One row per shipment |
| Hubs / carriers | 10 / 4 | Small broadcast dimensions |
| Delivered status | 18,402 | 92.0% of shipments |
| Delivered with a valid scan | 18,402 | On-time denominator |
| On-time rate | 81.36% | Delivered-only, scan-valid denominator |
| Average transit | 2.93 days | Mean hides the tail |
| p95 transit | 7.37 days | Tail used in contract review |
| Average cost | 35.50 | Per shipment, synthetic |
| Cost per kg | 8.71 | Excludes invalid weights |
| Exceptions | 357 | 1.79% of shipments |

Carrier scorecard:

| Carrier | Shipments | On-time rate | Avg transit | Exceptions |
|---|---:|---:|---:|---:|
| NileExpress | 5,025 | 89.60% | 2.53 d | 107 |
| MetroParcel | 4,969 | 84.78% | 2.78 d | 84 |
| SwiftLine | 5,023 | 80.77% | 2.98 d | 79 |
| GlobalFreight | 4,983 | 70.20% | 3.44 d | 87 |

Service-level view: Express is around 75% on time, while Economy and Standard are around
83–84%. The gap is a service-design question, not proof that one carrier is universally
bad. Carrier performance also varies by lane.

### Production notes

- Define whether the promise is a date, a timestamp, or a business-day promise, and version
  that definition.
- Normalize timestamps to UTC and retain local time for reporting.
- Allow a correction window for late scans; publish restatements with a version.
- Deduplicate scan events by shipment + milestone + event time.
- Validate carrier status codes; one carrier's "delivered" may be another's "handed to
  agent".
- Report missing-scan rate next to every on-time rate.
- A scorecard is a decision aid, not a contract; legal and procurement must agree on the
  definition before commercial use.

### Caveats

The lab simplifies a shipment to one delivery timestamp. A production parcel network has
many scan events, late feeds, and carrier-specific status mappings. The synthetic carrier
differences are teaching signals, not a real procurement recommendation.

## 7. Cross-case comparison

The four cases are deliberately different grains. Comparing them is the real lesson.

| Question | E-commerce | Telecom | Fraud | Logistics |
|---|---|---|---|---|
| Grain | Order line | Network event | Authorization | Shipment |
| Main denominator risk | Cancelled/returned orders | All events vs data events | All transactions vs labelled frauds | All shipments vs delivered with scan |
| Time semantics | Order month, cohort month | Event hour, busy hour | 10-minute event-time window | Promise vs delivery timestamp |
| Label availability | Status is immediate | No label; quality proxy | Labels arrive weeks later | Delivery scan may be late or missing |
| Tail metric | MoM growth, RFM | p95 latency | Recall by pattern | p95 transit |
| Main skew risk | Hot product | Hot cell | High-volume card | Hot lane/carrier |
| Main correctness trap | Revenue definition | Missing tower mapping | Label leakage | Missing delivery scan |

Three rules transfer to almost every pipeline:

1. **Write the grain and denominator down before the query.** Most metric disputes are
   definition disputes.
2. **A successful job is not correctness.** Reconcile totals, test invariants, and inspect
   the plan.
3. **Missing data is not a value.** Report completeness separately from the metric.
